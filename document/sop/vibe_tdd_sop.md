# 표준 운영 절차 (SOP): Vibe Coding TDD Workflow

## 1. 목적 (Purpose)
AI 에이전트 주도의 코드 구현 시 발생하는 결함과 보안 취약점을 최소화하기 위해, 테스트 주도 개발(TDD)과 서브에이전트 리뷰를 결합한 **바이브 코딩(Vibe Coding)** 방법론을 표준화합니다.

## 2. 적용 범위 (Scope)
모든 Redmine MCP 서버의 기능(Tool), 유틸리티, API 클라이언트 모듈의 신규 개발 및 수정 시 메인 에이전트(Antigravity)에 의해 적용됩니다.

## 3. 사전 준비 (Prerequisites)
- 테스트 러너: `vitest` 설치 및 설정 완료
- 백그라운드 훅: `.agents/hooks.json` 내 TypeScript 검사(`tsc --noEmit`) 활성화
- 서브에이전트: `security_code_reviewer` 정의 완료

## 4. 수행 절차 (Procedure)

### 단계 1: 실패하는 테스트 작성 (Write the Test - Red)
- **행동:** 대상 기능의 요구사항과 제약조건(입력값 검증, 예외 상황)을 커버하는 테스트 코드 작성.
- **명령어:** `./node_modules/.bin/vitest run <테스트_파일_경로>` (단일 파일은 로컬 바이너리를 직접 호출해 `npx` 다운로드 프롬프트를 피함)
- **검증:** 구현 코드가 없으므로, 테스트가 의도한 에러를 뿜으며 확실히 **실패(Fail)**해야 함.

### 단계 2: 최소 기능 구현 (Implement - Green)
- **행동:** 테스트를 통과시킬 수 있는 가장 간결하고 정확한 실제 코드를 작성.
- **명령어:** `./node_modules/.bin/vitest run <테스트_파일_경로>`
- **검증:** 편집 훅의 타입 검사 에러가 없어야 하며, 테스트가 모두 **성공(Pass)**해야 함. (실패 시 코드 수정 후 반복)

### 단계 3: 변경 등급별 서브에이전트 리뷰 (Tiered Subagent Review)
- **행동:** 변경의 위험도에 따라 리뷰 범위를 정합니다. 여러 등급에 해당하면 **가장 높은 등급**을 따릅니다. (DL-0029)

| 등급 | 해당 변경 | 리뷰어 |
|:--|:--|:--|
| **R0 생략** | 문서만 변경, 테스트만 추가, 주석·포맷팅 | 없음 (회귀 검증만) |
| **R1 품질** | 일반 기능·리팩터링 (아래 R2 경로를 건드리지 않음) | `deep_code_reviewer` |
| **R2 보안** | 인증·인가(`src/middleware/`), 쓰기 도구(`create_*`, `update_*`, `add_*`, `manage_*`, `upload_*`, `log*`), 외부 입력을 LLM에 반환하는 조회 경로, 전송 계층(`src/server/`, `src/index.ts`), 설정·환경변수, 의존성 추가, 가드레일(`.husky/`, `.agents/`, `.claude/`) | `deep_code_reviewer` + `security_code_reviewer` (병렬) |

- **검증:** 변경 파일 경로, 작업 목표, 판정한 등급과 이유를 넘겨 리뷰를 요청합니다. 리뷰어가 지적한 구조적 결함과 개선 사항을 적극 수용합니다. 등급 판정이 애매하면 높은 등급을 선택합니다.

### 단계 4: 결함 수정 루프 (Remediation Loop)
- **행동:** 서브에이전트가 지적한 결함이나 개선 사항을 처리.
- **규칙:** 단순 패치가 아닌, 해당 결함을 검증할 수 있는 **테스트를 먼저 추가(단계 1로 회귀)**한 후 코드를 수정.

### 단계 5: 최종 회귀 검증 및 마무리 (Regression Check)
- **명령어:** `npm test` (전체 테스트 스위트 + 커버리지 기준선 검사, pre-commit 과 동일). `npm test` 에 파일 인자를 붙이지 마십시오 — 일부 파일만 실행하면 전체 기준선에 미달해 항상 실패합니다. 같은 체크아웃에서 `npm test` 를 동시에 두 번 돌리지 마십시오(커버리지 디렉터리 잠금).
- **검증:** 기존·신규 기능이 모두 통과하고 커버리지가 `vitest.config.ts` 기준선 이상인지 확인 후, 사용자에게 최종 결과 요약 보고. 커버리지를 올렸다면 기준선도 함께 올립니다.

### 단계 6: 완료 보고 및 TO-DO 대기열 동기화 (Queue Completion)
- **서브에이전트:** 작업 브랜치에서 `document/todo.md`를 **수정하지 않습니다.** 대신 최종 보고에 브랜치명, 커밋 요약, 테스트 결과, 리뷰 반영 내역을 포함합니다. (병렬 브랜치 간 todo.md 병합 충돌 방지)
- **메인 에이전트:** 브랜치를 main에 병합한 직후 main에서 해당 항목을 `[x]` 처리하고 '완료된 작업 (Done)' 섹션으로 이동해 `docs(queue): ...` 로 커밋합니다.
- **규칙:** 병합 후 todo.md 동기화 없이 작업을 종료하는 것은 금지됩니다. (작업 완료 정의 필수 항목, DL-0028)

### 단계 7: 의사결정 문서화 판단 (Decision Logging)
- **행동:** 현재 작업을 진행하며 내린 기술적/실무적 결정이 있는지 스스로 검토합니다. (작성 조건은 AGENTS.md 6장)
- **규칙:**
  - 새로운 라이브러리 추가, 코딩 컨벤션 변경, 새 환경 변수 추가(`.env.example` 변경) 등이 있었다면 ➡️ `document/templates/decision_log_template.md`를 사용해 **DL 작성**
  - 전체 시스템 구조 변경, 보안 모델 변경 등이 있었다면 ➡️ `document/templates/adr_template.md`를 사용해 **ADR 작성**
  - 문서를 작성했다면 반드시 `document/index.md`에 동기화(업데이트)해야 합니다.

## 5. 예외 처리 및 복구
- 훅(Hook) 실행 에러 발생 시: 타입 검사 로그(Antigravity `.agents/typecheck.log`, Claude Code `.claude/typecheck.log`)를 확인하여 문법/타입 에러 즉각 수정.
- pre-commit 의 `⚠️ [Test Warning]`(src 변경에 테스트 변경 없음)은 차단이 아니지만, 순수 리팩터링이 아니라면 1단계를 건너뛴 것이므로 테스트를 보완합니다.
- 무한 루프 방지: 서브에이전트와 의견이 충돌하거나 테스트 통과가 3회 이상 실패 시, 작업을 중단하고 사용자에게 피드백 요청.
- 서브에이전트 워크트리 규칙 및 무한 대기 방지:
  - `invoke_subagent(Workspace: share)` 호출 시 시스템이 자동으로 격리된 워크트리를 제공하므로, 서브에이전트는 내부에서 별도로 `git worktree add` 명령을 사용해 중첩된 워크트리를 만들지 말고 제공된 환경을 그대로 사용해야 합니다.
  - 서브에이전트가 격리된 워크트리(`Workspace: share`)에서 작업을 시작할 때 `node_modules`가 없다면, 서브에이전트 스스로 `npm install`을 실행하되 **절대 샌드박스 우회(BypassSandbox)를 사용하지 말고 기본 샌드박스 환경에서 조용히 설치**해야 합니다.
  - 서브에이전트는 백그라운드 태스크로 `npx` 등을 사용할 때 다운로드 프롬프트에 막히지 않도록, 로컬에 기설치된 바이너리(예: `./node_modules/.bin/vitest`)를 직접 지정하여 실행해야 합니다.
  - 메인 에이전트는 서브에이전트 호출 시 10분 Liveness Timer(`schedule` 도구)를 설정하여 무응답 시 자동 조치되도록 방어합니다.

## 6. 에이전트 무한 루프 방지 지침 (Anti-Loop Mitigation)
- **대기열(Queue) 경고는 차단이 아닙니다**: `⚠️ [Queue Warning]`은 경고일 뿐 커밋은 성공합니다(DL-0002). 경고를 해소하려고 `todo.md`의 순서를 바꾸지 마십시오. 순서 변경은 사용자 승인 대상입니다(AGENTS.md 8장).
- **커밋이 실제로 차단된 경우** (`❌` 메시지, exit code ≠ 0):
  1. 훅 출력의 원인(허용 경로 위반, 문서 인덱스 누락, 타입 에러, 테스트 실패, 커밋 메시지 규칙)을 읽고 **원인을 수정한 뒤** 다시 커밋합니다. 같은 커밋을 그대로 재시도하지 마십시오.
  2. 허용 경로 위반(main 저장소)이라면 코드를 고치지 말고 워크트리로 작업 위치를 옮기십시오.
  3. 원인 수정 후에도 같은 단계에서 3회 이상 차단되면 작업을 중단하고 부모 에이전트(혹은 사용자)에게 훅 출력 전문과 함께 보고하십시오.
