# 표준 운영 절차 (SOP): Vibe Coding TDD Workflow

## 1. 목적 (Purpose)
AI 에이전트 주도의 코드 구현 시 발생하는 결함과 보안 취약점을 최소화하기 위해, 테스트 주도 개발(TDD)과 서브에이전트 리뷰를 결합한 **바이브 코딩(Vibe Coding)** 방법론을 표준화합니다.

## 2. 적용 범위 (Scope)
모든 Redmine MCP 서버의 기능(Tool), 유틸리티, API 클라이언트 모듈의 신규 개발 및 수정 시 메인 에이전트(Antigravity)에 의해 적용됩니다.

## 3. 사전 준비 (Prerequisites)
- 테스트 러너: `vitest` 설치 및 설정 완료
- 백그라운드 훅: `.agents/hooks.json` 내 TypeScript 검사(`tsc --noEmit`) 활성화
- 서브에이전트: `security_code_reviewer` 정의 완료

## 4. 수행 절차 (Procedure)

### 단계 1: 실패하는 테스트 작성 (Write the Test - Red)
- **행동:** 대상 기능의 요구사항과 제약조건(입력값 검증, 예외 상황)을 커버하는 테스트 코드 작성.
- **명령어:** `npx vitest run <테스트_파일_경로>`
- **검증:** 구현 코드가 없으므로, 테스트가 의도한 에러를 뿜으며 확실히 **실패(Fail)**해야 함.

### 단계 2: 최소 기능 구현 (Implement - Green)
- **행동:** 테스트를 통과시킬 수 있는 가장 간결하고 정확한 실제 코드를 작성.
- **명령어:** `npx vitest run <테스트_파일_경로>`
- **검증:** 훅(Hook)의 백그라운드 구문 오류가 없어야 하며, 테스트가 모두 **성공(Pass)**해야 함. (실패 시 코드 수정 후 반복)

### 단계 3: 정밀 다각도 검증 (Deep Subagent Review)
- **행동:** 코드의 품질, 아키텍처, 엣지 케이스 및 보안을 모두 아우르는 `/boost` 수준의 정밀 리뷰 수행.
- **도구:** 일반 작업 시에도 `invoke_subagent`를 사용하여 아래의 리뷰어를 필수적으로 호출합니다.
  1. 대상: `deep_code_reviewer` (아키텍처, 엣지 케이스, 비즈니스 로직, TDD 준수 등 전반적 품질 검토)
  2. 대상: `security_code_reviewer` (취약점 및 보안 모델 검토)
- **검증:** 수정된 파일 경로와 작업 목표를 넘겨 리뷰를 요청합니다. 리뷰어들이 지적한 구조적 결함이나 개선 사항(코드 스멜)을 적극 수용해야 합니다.

### 단계 4: 결함 수정 루프 (Remediation Loop)
- **행동:** 서브에이전트가 지적한 결함이나 개선 사항을 처리.
- **규칙:** 단순 패치가 아닌, 해당 결함을 검증할 수 있는 **테스트를 먼저 추가(단계 1로 회귀)**한 후 코드를 수정.

### 단계 5: 최종 회귀 검증 및 마무리 (Regression Check)
- **명령어:** `npx vitest run` (전체 테스트 스위트 실행)
- **검증:** 기존 기능과 신규 기능이 모두 완벽히 동작하는지 확인 후, 사용자에게 최종 결과 요약 보고.

### 단계 6: TO-DO 대기열 완료 동기화 (Queue Completion)
- **행동:** 기능 구현과 테스트 통과, 코드 리뷰가 모두 완료되면, 서브에이전트는 반드시 `document/todo.md`를 열람하여 자신의 작업 항목을 대기열에서 찾아 `[x]` 완료 처리하거나 '완료된 작업 (Done)' 섹션으로 이동시킨 후 변경사항과 함께 커밋합니다.
- **규칙:** `document/todo.md` 동기화 없이 소스 코드만 단독 커밋하는 것은 금지됩니다. (작업 완료 정의 필수 항목)

### 단계 7: 의사결정 문서화 판단 (Decision Logging)
- **행동:** 현재 작업을 진행하며 내린 기술적/실무적 결정이 있는지 스스로 검토합니다.
- **규칙:**
  - 새로운 라이브러리 추가, 코딩 컨벤션 변경, 환경 변수 추가 등이 있었다면 ➡️ `document/templates/decision_log_template.md`를 사용해 **DL 작성**
  - 전체 시스템 구조 변경, 보안 모델 변경 등이 있었다면 ➡️ `document/templates/adr_template.md`를 사용해 **ADR 작성**
  - 문서를 작성했다면 반드시 `document/index.md`에 동기화(업데이트)해야 합니다.

## 5. 예외 처리 및 복구
- 훅(Hook) 실행 에러 발생 시: `.agents/typecheck.log`를 확인하여 문법/타입 에러 즉각 수정.
- 무한 루프 방지: 서브에이전트와 의견이 충돌하거나 테스트 통과가 3회 이상 실패 시, 작업을 중단하고 사용자에게 피드백 요청.
- 서브에이전트 워크트리 규칙 및 무한 대기 방지:\n  - `invoke_subagent(Workspace: share)` 호출 시 시스템이 자동으로 격리된 워크트리를 제공하므로, 서브에이전트는 내부에서 별도로 `git worktree add` 명령을 사용해 중첩된 워크트리를 만들지 말고 제공된 환경을 그대로 사용해야 합니다.
  - 서브에이전트가 격리된 워크트리(`Workspace: share`)에서 작업을 시작할 때 `node_modules`가 없다면, 서브에이전트 스스로 `npm install`을 실행하되 **절대 샌드박스 우회(BypassSandbox)를 사용하지 말고 기본 샌드박스 환경에서 조용히 설치**해야 합니다.
  - 서브에이전트는 백그라운드 태스크로 `npx` 등을 사용할 때 다운로드 프롬프트에 막히지 않도록, 로컬에 기설치된 바이너리(예: `./node_modules/.bin/vitest`)를 직접 지정하여 실행해야 합니다.
  - 메인 에이전트는 서브에이전트 호출 시 10분 Liveness Timer(`schedule` 도구)를 설정하여 무응답 시 자동 조치되도록 방어합니다.

## 6. 에이전트 무한 루프 방지 지침 (Anti-Loop Mitigation)
- **대기열(Queue) 검증 에러**: `git commit` 시 Husky의 `pre-commit` 훅에서 "작업 순서 위반 (Queue Error)"이 발생하며 커밋이 차단되는 경우, **절대로 커밋을 맹목적으로 재시도하지 마십시오.** 
- 훅이 차단하는 이유는 현재 체크아웃한 브랜치명이 `document/todo.md`의 1순위 항목과 일치하지 않기 때문입니다.
- **해결책**:
  1. 먼저 `document/todo.md`의 내용을 열람(`view_file`)하여 대기열 상태를 확인하십시오.
  2. 에이전트 스스로 큐를 갱신할 권한(메인 에이전트 등)이 있다면 `todo.md`를 수정하여 자신의 브랜치를 1순위로 올린 후 다시 커밋하십시오.
  3. 만약 서브 에이전트로서 큐 갱신 권한이 없다면, 즉시 작업을 중단(Stop)하고 "대기열 불일치로 커밋할 수 없습니다"라고 부모 에이전트(혹은 사용자)에게 보고하여 개입을 요청하십시오.
